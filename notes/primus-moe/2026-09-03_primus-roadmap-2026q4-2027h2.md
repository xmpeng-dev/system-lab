## 0. 执行摘要

三句话版本：

1. **Primus 最大的风险不是性能，是上游欠债。** 156 个 patch 里只有 1 个声明版本门，而 Megatron 已经落后 1391 commits（core 0.16→0.20）、TorchTitan 落后 937 commits（+168K 行）。上游同时废弃了 `GPTModel`、删除了 `megatron/legacy/`。下一次升级不是 rebase，是硬切。
2. **两个上游官方扩展点刚刚就位，这是一个时间敏感的战略窗口。** Megatron 的 `BackendSpecProvider`（2026-08-21 `881dc7605` 转正）和 TorchTitan 的 `torchtitan/overrides/` 都是为"厂商注入 kernel"设计的，而且上游自己在用。把 monkey-patch 转成受支持插件，是唯一能从结构上降低维护成本的动作。
3. **护城河已被实证，比预想的宽。** 上游 Megatron 的 `megatron/core/` 里 ROCm 相关命中 1 处、`torch.cuda.` 调用 796 处，无设备抽象层；上游 TorchTitan 直接停掉了 ROCm CI、删掉 ROCm golden loss、把 ROCm 排除在发版验证之外、并把 AMD 用户指向独立 fork。zero-bubble / DualPipe 在上游 Megatron 是 **0 命中**。

优先级排序原则：**先修可信度（度量 + 正确性 CI），再修结构（插件化 + 版本门），再收性能红利（已根因定位的存量项），最后投研究线。** 顺序反了会导致"拿噪声数据去驱动架构决策"。

## 1. 定位判断

### 1.1 Primus 是什么

不是"Megatron 的 AMD 封装"。按代码事实：`primus/` 有 21.4 万行 Python，其中 patch 层只占 megatron 后端的 17%，而 `primus/core/pipeline_parallel/`（8,975 行）单独就超过全部 megatron patch（7,975 行）。**Primus 里已经有约 33,000 行执行层代码在生产运行，只是它们分散在三个 backend 命名空间里，没有被当作一个执行层来管理。**

这决定了对外叙事和内部立项的措辞：不是"请批准我们造一个框架"，而是"我们已经有一个执行层，请批准把它从三个 backend 命名空间里收拢出来"。（`notes/primus-moe/2026-08-04_1018_framework-strategy-patch-layer-vs-execution-layer.md`）

### 1.2 上游取舍矩阵

| 判断 | 内容 | 依据 |
|---|---|---|
| **停手**（上游正在或已吸收） | MoE dispatch / EP 通信逻辑本身（上游已 4 条 dispatcher 路径）、1F1B+A2A overlap、细粒度重算与激活卸载、FP8 recipe 全矩阵、HF checkpoint 互操作（归 Megatron-Bridge）、inference / RL refit、Muon/SOAP/Lion 优化器、自研 FSDP（MFSDP v1 已覆盖 ZeRO-1/2/3+HSDP+EP+MXFP8） | 上游 Megatron 调研 §"about to absorb" |
| **必须追赶**（上游破坏性变更） | `GPTModel`→`HybridModel`、`parallel_state` 全局量→`ProcessGroupCollection`、TE 版本格（~25 个版本谓词）、TorchTitan TOML→Python dataclass 配置 + `spmd_types` 默认 + `ShardingConfig` + `config_registry.py` 删除（无 shim） | 两份上游调研 §"version-alignment risks" |
| **独占**（上游不会做） | ROCm 全栈持续验证、ROCm grouped GEMM（上游 `LocalSpecProvider` 明确留空）、zero-bubble / DualPipe 调度、ROCm MoE 通信（DeepEP/HybridEP 两个上游都无 ROCm 路径）、量化 collective（无人认领）、容量规划（上游删掉了 estimation 脚本）、MI300A APU 统一内存 CPU offload | 本文 §1.3 |

## 2. 现状资产盘点（优异点）

以下都是已落地、有实测数字支撑的差异化能力，可直接用于对外叙事。

### 2.1 MoE 融合执行：MegaMoE

FlyDSL 实现的融合 MoE 层，把 expert all-to-all 折进喂给它的 grouped GEMM。

- kernel 级 **1.51×**，端到端最高 **1.123×**
- **与低精度叠加增益**：MXFP8 下 1.123× > BF16 下 1.082×，因为量化其他部分后 MoE 在 step 中占比上升
- 同时降峰值显存：MXFP8 配对下 **142.4 GiB vs 150.1 GiB**，因为置换后的 token buffer 从未落地
- 加速比在故意制造的路由不均衡下不变，即不依赖专家负载均匀

（`docs/tech_blogs/primus-moe-optimization/README.md`）

### 2.2 低精度 grouped GEMM

- FP8（tensorwise）grouped GEMM 相对 BF16：前向随 M 增长 **1.2×@M=2048 → 1.6×@M=8192**，反向稳定 **1.5–1.7×**（含量化开销计入 FP8 侧）
- Turbo + FlyDSL 附加开关在已含基础优化的配置上再加 **Qwen3-235B-A22B +16.2% / GPT-OSS 20B +9.7% / Qwen3-30B-A3B +5.8%**
- 反向收益更大，而反向本身是这一层的大头

### 2.3 大规模稳定性实证

DeepSeek-V3，1024× MI355X：

- 调优后的 pipeline layout + 按规模显式 recompute ID → **1.095×** 基线吞吐
- 边界 rank 气泡 30.6% / 35.1% → **22.0% / 11.7%**
- **1700 连续步**：中位步时 22.08 s，**93.2% 的步在 ±2% 内**，10.6 小时漂移 **1.8%**
- 扩展性：固定配置下 128 节点保持 32 节点单卡吞吐的 **98.5%**（4× 卡数只损失 1.5%）；按规模重调后达 **104.1%**（更宽的 DP 组省出显存，重算从 15 层降到 9 层）

### 2.4 训练前规划：Primus Projection

- 41 个文件、15 个模块 profiler、13,394 行，含 Origami GEMM + SDPA 模拟器
- 已发布验证案例**全部落在实测 10% 以内**，MoE 案例（8 节点 Mixtral 8x22B, EP8/PP4/VPP2）**1.4%**
- 有纯 CPU 模拟模式，不需要 GPU
- 是 Primus Tuning Agent 的打分 oracle
- **上游对标物为空**：TorchTitan 只有一个 SLURM 文件，且在 #2386 里把 `scripts/estimate/estimation.py` 删了

### 2.5 流水线调度家族

31 个 scheduler 文件，覆盖 zb / zbv / zbv_greedy / v1f1b / vpp / seq1f1b / token 级 ZB / auto-schedule / offloading，另有 6 个算法的独立实现、`primuspipe/` handler 运行时、PP 可视化器、ODC（基于 ROCm/MORI + rocSHMEM 的按需通信）。

**上游 Megatron 的 zero-bubble / DualPipe 命中为 0。** 这是当前领先且短期无碰撞风险的一块。

### 2.6 JAX 路径的 dropless MoE

grouped GEMM + DeepEP 让纯 JAX 做不到的配置变得可行：

- 移除约 **444 GiB** 的 expert-matmul 墙；DeepEP 更瘦的 all-to-all 降低约 15% 瞬时占用，换回一档 batch size
- per-device batch 8–9 可行，而 `ragged_all_to_all` dropless 路径在 8 就 OOM
- 约 **1180 tokens/s/device**，在所有可行 batch size 上优于 `ragged_all_to_all`，达到 `capacity_factor=4` 稠密配置的约 **2×**

### 2.7 工程可信度资产（被低估的差异化）

- **`primus/core/config/schema_check.py`（1,200 行）**：AST 静态读上游 schema（不 import torch/jax），从 `get_param()` 调用和 dataclass 子类推导合法扩展而非维护手写清单，进 CI `code-lint`。**它的存在源于一次真实事故**——`debug_moe_force_load_balance` 被上游改名，导致"所有 DeepSeek 配置都在关着 MoE 负载均衡的情况下训练"。手写逃生舱只有 79 行。
- **DeepEP 静默错梯度根因定位**（`report/deepep-bf16-loss-investigation.md`，620 行）：DeepSeek-V3 BF16 loss 开 DeepEP 卡在 6.1 vs 关闭 4.52。推翻约 10 个假设、自建 5 个 GPU 探针，其中发现**探针自身会掩盖 bug**（backward hook 里的 host I/O 让复现率 6/6 → 0/6）。根因是 `intranode.hip:365-369` 的 `kUseCheapFence` 只做编译器 fence + per-wave `s_waitcnt` + relaxed store，其他 warp 写的数据没有 system-scope 写回、接收端读到 stale L2。验证 0/8 vs 13 坏行，loss 4.5214 vs 参考 4.5213，代价 +2.5%。已修进上游并由 `4d2f7a74`(#1048) 取回。

这两件事讲的是同一个故事：**Primus 有能力发现并根治别人发现不了的静默正确性问题。** 对企业客户，这比多 5% 吞吐更值钱。

## 3. Roadmap

### 阶段 C0 — 可信度地基（2026 Q4，约 6–8 周）

> 这一阶段不产出新功能。它的唯一目的是让后续所有性能与架构决策"可被验证"。跳过它，后面每个数字都是可争议的。

| ID | 条目 | 验收标准 |
|---|---|---|
| **C0-1** | **度量可判定性标准**：固定时钟（或选定展散最小的卡并锁定）、报告比值与 PMC 计数而非绝对值、30+ 次重复给出分布、记录环境指纹。同时修节点配置（`rocm-smi --setperflevel high` 当前 "Not supported"，sclk 在 level 0/1 间跳，绝对值摆动 ±30%） | 任何对外/立项数字附带分布与指纹；<10% 的结论在修复前不得引用。这同时是 Pilot BASELINE 非确定性（已阻塞 15 个月）的同一根因 |
| **C0-2** | **patch 层失败可见化**：`_get_backend_version()` 当前吞异常返回 `None`，`_match_backend_version()` 随即返回 `False` → **静默跳过**。改为 fail-loud；启动时打印"期望 vs 实际"的 patch 清单并在不匹配时退出；重复 patch id 报错；`_patch_guard` 提升进 core 并扩到 TorchTitan | 上游挪动 `package_info.py` 时训练**拒绝启动**而非静默降级。**必须在 C0-3 之前完成**——先补版本门会让一次探测失败禁掉整个 patch 层 |

### 阶段 C1 — 插件化与上游对齐（2026 Q4 – 2027 Q1）

> 战略窗口期。两个上游扩展点都是新的，现在介入既能少写 patch，也能影响接口形状。

### 阶段 C2 — 存量性能红利（2027 Q1 – Q2）

> 全部已根因定位，属于"kernel 已经做完、包装层是 bug"类型，ROI 最高。

| ID | 条目 | 量化依据 |
|---|---|---|
| **C2-1** | **修 Primus DataLoader**（Bridge `dataset_provider` 用 spawn multiprocessing context）；并把 `fp8_param` / precision recipe 暴露到 yaml | Llama-2-70B LoRA 上 Primus vs NeMo **8.4% 步时差距的全部**是一个 191 ms 单进程 DataLoader 空转（8192² mask 构造约 125 ms 在主线程）。修完应**反超 NeMo**。另有约 70/85 GB 显存差距来自 `fp8_param=True` 运行时强制覆盖且 yaml 里不可见——本身就是可用性缺陷 |

> slab 的 10k GPU 差距分析把这一类评为**最高影响 × 最低覆盖**。当前 Primus 的答案是人工 SOP。

| **C3-7** | **全迭代 HIP graph 捕获 + 统一 DP/PP/TP/EP 通信重叠调度器** | 是每步八个决策点中的第八个、**当前 0 行**，且*"无法作为 monkey-patch 干净实现"*（捕获一步需要拥有它的控制流）。前置条件：plan 中**不含数据相关控制流**，故必须排在 IR 合并与精度显式化之后。NVIDIA 数据显示与同步消除结合后收益很大：**DeepSeek-V3 +8%、GPT-OSS +93%**；AMD 自己 MLPerf Flux 的 HIP graph 捕获拿到 +5.3%。⚠ 与 C3-1/C3-2 有张力：EEP 指出 graph 烘焙的路由元数据是弹性的障碍，**roadmap 必须显式排序** |

## 4. 风险与护栏

以下是调研中**反对本 roadmap 部分内容**的证据，必须作为护栏读，不能省略。

| 风险 / 反证 | 影响的条目 |
|---|---|
| **融合持久化 kernel 在文献中被直接批评**（资源刚性划分 + 软件轮询）——UBEP §6 是*"ROCmoe 路线必须正面回答的论文"*；ExpertPlex 另证自适应持久 kernel 优于静态空间划分 | C2-6, C4-5 |
| **Alibaba 生产系统拒绝了 Comet 式融合**（后端耦合），并实测 **EP 通信 kernel 占约 20 SM 造成 10–20% 变慢**；Motif 3 独立佐证*"规模上消除 expert 权重 All-Gather 优于隐藏它"*。即**通信应被消除或卸载，而非仅仅重叠**。Meta 的答案是硬件（MTIA 300 消息引擎），AMD 只能软件解 | C2-6, C3-4 |
| **多机 RDMA 可吃掉整个单机 megakernel 优势**——Perseus 实测 8 节点最多 **10× 退化**，*"节点内不存在此问题"*。而本工作区验证过的一切都是单机 8× MI355X | C2-6, C4-5 |
| **cost model 尾部误差会翻转 MILP 排序**——Tessera 报告 **15% 尾误差即反转排名**，为任何 predicate/projection 驱动的决策设了硬精度门槛 | C1-7, C4-2, C4-5 |
| **AutoMegaKernel 的负面结果**：megakernel 瓶颈是 **per-tile 跨 SM 同步，且在带宽最高的训练级芯片上最严重**——恰是目标硬件 | C4-5, C4-6 |
| **按 token 数分桶的静态 kernel dispatch 是错的**——DA-MoE 显示最优融合 MoE kernel 随路由偏斜与 token 数变化，应做 GPU 常驻运行时 dispatch | C2-4, C2-7 |

| **hipBLASLt 的"选择优势" vs 单配置特化**：hipBLASLt 靠按 shape 运行时挑 tile 在大 BS 上胜出（−5.8%/−7.9%），但小 BS 上差 1.8–2.1× 且有 hang。融合 kernel 内 shape 编译期已知故特化胜出——**这说明融合路径与库路径有真正不同的最优区间，必须做 predicate 而非全局开关** | C2-4, C2-6 |
| **"84% stall 可回收"是谬误**：MFMA issue 已饱和的 kernel 在 ATT 里显示的 barrier/wait 周期与调度糟糕的 kernel 相同。已在 `fc1_dgrad` 上独立证明——移除同步指令**墙钟不变**，因为 barrier stall 反映的是 epilogue 跨波散兵而非同步成本 | C0-1, C2-6 |
| **三次自我纠错说明调错工作负载有多容易**：`tokens_per_gpu` 读错作废了 14 个优化循环；"FC1 ≈ 1.5 ms"实为 3.247 ms（把重叠上限从 50% 翻到 100%）；"cluster" 路由把 dispatch 压缩约 6×，**绝不可当作 Primus 性能引用**。**任何 roadmap 基准定义必须显式锁定负载语义** | C0-1, X-1 |
| **方案 C 的执行风险**：*"若把这个项目当成'开发一堆组件'来推，它会退化成零件箱——局部最优的组件、没有统一的 plan，最终既无差异化也无产品故事。守住 plan/execute 分离是前提，不是实现细节。"* 且目标架构**未经生产验证**（仅 2 个测试 yaml），迁移必须双栈并行而非切换 | C4-1, C4-2 |
| **FP4 随机性问题未决**：Penn State + AMD 在 MI355X **原生** MXFP4 上测得达到 ppl 3.3 的 token 成本 Fprop 8–9% → +Dgrad 10–11% → **+Wgrad 26–27%**；随机舍入与随机 Hadamard **不收敛**，确定性 Hadamard 恢复到 8–9%。单步 +20% 吞吐端到端只剩 **+9–10%**。**与 NVIDIA 直接冲突**（TE `NVFP4BlockScaling` 默认随机舍入 + RHT）。**无跨厂商独立复现**。且该论文与 MLPerf 博客**不是独立来源**（同团队同流水线），并且**只做稠密、完全没碰 MoE / grouped GEMM** | C3-5 |

## 5. 对外叙事（优异点摘要）

给客户/管理层的一页版本，全部有实测支撑：

1. **AMD 上唯一被持续验证的多后端训练框架。** 上游 TorchTitan 已停掉 ROCm CI、删除 ROCm golden、把 ROCm 排除在发版验证之外；上游 Megatron 的 core 里 ROCm 相关代码 1 处、`torch.cuda` 调用 796 处。Primus 是这条路径上唯一有人守的地方。
2. **MoE 融合执行领先。** MegaMoE kernel 级 1.51×、端到端 1.123×，且**与低精度叠加**（MXFP8 下比 BF16 下更划算）并**降低峰值显存**。上游没有对标物。
3. **大规模实证，不是 demo。** DeepSeek-V3 在 1024× MI355X 上 1.095× 基线，1700 连续步中位 22.08 s、93.2% 在 ±2% 内、10.6 小时漂移 1.8%；128 节点保持 32 节点单卡吞吐 98.5%。
4. **训练前就能回答"装得下吗、多快"。** Projection 全部发布案例误差 ≤10%，MoE 案例 1.4%，且有纯 CPU 模式。上游把自己的估算脚本删了。
5. **调度能力上游没有。** zero-bubble / DualPipe 家族在上游 Megatron 是 0 命中，Primus 有 31 个 scheduler 文件的实现。
6. **能发现并根治别人发现不了的静默正确性问题。** DeepEP 的 `kUseCheapFence` 内存序 bug 导致静默错梯度（loss 6.1 vs 4.52），根因定位后修进上游；`schema_check.py` 把一次"所有 DeepSeek 配置都在关着负载均衡训练"的事故变成了 CI 门禁。对企业客户，这比多 5% 吞吐更值钱。
