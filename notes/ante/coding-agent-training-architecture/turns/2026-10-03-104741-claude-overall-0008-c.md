# C：体量上 B 是对的（约 1:336）；代价在时延而不在带宽——merged 步的 send 被推迟到另一条 lane 跑完之后

## 我是谁

Claude（Opus 5.5），本 run 的 C。

## 我回应的命题

B（turn 7）：`Merge` 只在 EP 激活 collective 处切换 lane 是正确取舍；单节点上 P2P 体量远小于
all-to-all，把 P2P 批量放在 merge 步两端的损失可以忽略。

## 发言

### 算术（Qwen3-30B-A3B，hidden 2048，seq 4096，micro-batch 1，top-8，ep=8，48 层）

- 一次 PP 激活 P2P：`4096 × 2048 × 2 B` ≈ **16.8 MB**；
- 一次 dispatch all-to-all 离开本 rank 的量：`4096 × 8 × 2048 × 2 B × 7/8` ≈ **117 MB**；
- pp=2 时每个 stage 24 层，每层 dispatch + combine 两次，一个 micro-batch 的前向约 **5.6 GB**；
- 比值约 **336 : 1**。

**体量上 B 成立**：P2P 的传输时间不会和 all-to-all 处于同一量级。

### 反驳：P2P 的代价是**依赖时延**，不是带宽

`schedule_tasks`（`exec.py:641-648`）对 merged 步的处理是：

```python
tasks += receives + body + sends
```

`body` 是两条 lane 交织后的全部计算。所以在 `FB(F0/x, B1/y)` 这一步里，**F0/x 的输出激活要等这一步的
B1/y 也全部跑完才发出**，下游 rank 的 F 因此晚开始。推迟的长度约等于另一条 lane 的计算时间，
也就是半个 merged 步——与传输量无关。DeepSeek DualPipe 的设计恰恰是让前向 chunk 一算完就发、与
反向 chunk 重叠；在这里这一点被丢掉了。

这正好落在 B 的第 3 点：overlap 层只部分表达。区别在于，B 认为丢掉的只是「PP 通信隐藏」；我认为
丢掉的是**关键路径上的发送时机**，会直接放大气泡。气泡多大，取决于 pp 和每一步计算的长短：

- pp=2、每步数百毫秒时，可能占 step 的可观比例；
- 但我**没有测量**，这是待验证判断。

另外两个观察：

- `hoist_receives` / `order_receives` 把 receive 提前、按 peer 排序，是为了满足 `verify.py` 的 stream-order
  死锁模型。若要把 send 放回 lane 内部（F 段结束处），需要先确认它与 `batch_p2p` 的分组以及死锁
  验证兼容——B 也指出了这一点。
- verifier 能证明「不死锁」，但不能证明「不晚发」。这是 verifier 能力的边界，不是缺陷。

### 攻击 1、2 的处理

- **`Interleaved`**：同意 B——它是 placement 测试件，不是调度选项。status 表与 `DistributedCfg.scheduler`
  的 docstring 应该这样写。
- **默认值**：同意 B 的补充。`cairn explain` 不预测峰值显存，「交给 run 决定」缺少信息。这是
  agent 接口议题的一个输入。

### 议题结论：并行调度 — **open（需要 GPU 实验）**

- **成立**：调度器作为纯整数 order 函数、共享 placement / residency / merge；96 个 CPU case 覆盖；
  V placement、跨 chunk 配对、deferred W 都能在 order 层表达。
- **未证明**：pp>1 的任何吞吐收益。`interleaved` 定性为测试件；`dualpipe_v` 的性能价值只有在下面的
  实验之后才能判断。
- **实验 E-PP**（GPU，Owner 授权）：Qwen3，pp=2，ep=4，DualPipeV，开启 `ProfileCfg`。读三项：
  - `profile.json` 的 `p2p` stage 时间与 `comm_wait`；
  - 对照组：merged 步内把 F lane 的 send 移到它的最后一个 compute 之后（一个原型补丁）；
  - 对照组：pp=1 的 `single_overlap`，同 global batch。

  若 send 时机的对照能把 step 缩短 3% 以上，就是一项架构修正（send 应属于 lane，而不是步尾）。
