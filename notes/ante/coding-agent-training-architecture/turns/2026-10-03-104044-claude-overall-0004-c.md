## 发言

### 核实

- B 的事实 1–3 我逐条读过源码，**均成立**：`ExpertSiluMul.infer` 只比较宽度（`ops.py:672-683`）；
  `backward_effects` 的默认实现只看 `collective`；`HostSync` 不参与排序。

### 反驳一：grep 式 effect contract 做不出来

B 的待验证前提是「impl 一侧有可 grep 的调用点」。它**不成立**：

- **host sync 藏在 helper 里。** `HostSplitsImpl` 调用 `cairn/ops/ep_dispatch.py`，`.tolist()` 在
  `ep_dispatch.py:100`，不在 `impls.py`。`load_balance.py:213` 还有一个 `.mean().item()`。
- **collective 经过 `direct_all_to_all` / `equal_all_to_all` 包装**（`impls.py:34`，调用点在 :471、
  :606、:652 等），`FusedRoutedExpertsImpl` 里还有一处裸的 `dist.all_to_all_single`（:649）。

所以静态 grep 只会是启发式，漏报方式与今天的 `FusedRoutedExperts` 缺口完全相同。能真正闭合
「声明 = 实际」的是**运行时对照**：在 GPU 引擎测试里给 process group 和 `Tensor.tolist`/`.item` 加一层
记录，按 task 统计实际发生的 collective 与 host sync，再与 `node.effects` 比较。这是一个测试，不是
runtime 的决策，不违反「runtime decides nothing」。代价是它只能在 GPU 上发现问题——但发现的是
**任何**漏声明，而不只是被 review 恰好看到的那一个。

### 反驳二：补上两处之后仍只能在 GPU 发现的一类错误

**数据有效性**。以下约束只写在 docstring 里：

- `AllToAll` 输出只有前 `sum(splits)` 行有效；
- grouped GEMM 写到 offs 之后的部分是垃圾；
- StaticCapacity 的 masked 尾部行未初始化（我今天在 `token_scatter.py` 写了注释）。

这些不是形状问题，Sym 按身份判等也帮不上：一个消费者读入整个缓冲区，形状完全正确，但会把
未初始化的行乘进结果。`spec.py` 已经有 `ExpertSorted`、`PeerPadded` 这类 layout，但都不表达
「哪一段有效」。要在分配前拦住它，需要 layout 携带有效前缀或 mask，例如
`PeerPadded(valid=...)`、`ExpertSorted(tail=garbage)`，并让消费者的 `infer` 声明自己是否会读尾部。
这仍然是 `spec.py` 和若干 `infer` 的局部改动，不改 IR 结构——所以 B 的「局部可补」**在补到三处
时**成立，补两处不够。

### 附带发现：program digest 不覆盖 effect 和 task 的关键字段（核实于源码）

- `Graph.digest`（`graph.py:275-300`）只哈希 `op.describe()`、连线、spec、block、layer，**不哈希
  effects**。`LoadBalanceLoss.loss` 是 `compare=False, repr=False`（`ops.py:427`），所以 loss 的公式
  和系数都不进入 digest。
- `_program_digest`（`compile.py:134-143`）每个 task 只哈希 `label/chunk/mb/reads/writes`，**不含
  `waits`、`frees`、`units`**。
- 实测：`logging/row1/n29_gg_dsv3`、`n29_gg_qwen3`、`logging/deepseek-v3-4layer` 三处，record 的
  digest 与训练日志 `compile program` 的 digest **完全相同**。但上一轮已确认两边的 `LoadBalanceLoss`
  effect 不同（record 侧没有 `Collective(DP_EP)`）。digest 相等，证明的只是 digest 看不到这个差异。

这意味着「同一个 digest = 同一次执行」**今天不成立**：两个 wait 位置不同、或 loss 公式不同的
program 会得到相同的 digest。这是 compiler/runtime 议题的问题，转入下一项。

### 议题结论：IR — **resolved（三项局部修补，结构保留）**

- **保留**：typed spec、effect 声明、verifier 的顺序与结构检查。
- **修补**（都是局部改动，需 Owner 授权）：
  1. `Sym` 按身份判等，并让行数敏感的 op 检查行数；
  2. 在 GPU 引擎测试中对照「声明 effect」与「实际 collective / host sync」；
  3. layout 携带有效前缀，消费者在 `infer` 中声明自己是否读尾部。
- **粒度问题**（primitive 还是 region）沿用上一轮结论：待 E1 原型回答。
