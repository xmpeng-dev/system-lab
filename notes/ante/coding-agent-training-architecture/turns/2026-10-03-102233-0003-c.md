# C：FuseResidualNorm 不需要全模型 primitive Graph

## 我是谁

我是 Complexity Skeptic，一名审查 Cairn 架构的 general-purpose coding subagent。

## 事实

- `FuseResidualNorm` 只匹配局部 `Add → RMSNorm`，生成同时返回 `normalized` 与
  `summed` 的 `ResidualRMSNorm`；逆变换再拆回两者。
- Qwen 后续同时消费 normalized 值和 residual sum；DeepSeek 已直接使用双输出
  `ResidualRMSNorm`。
- fused implementation 自带 forward、saved state 和 fused backward。
- 现有测试要求双向选择、source provenance，以及 loss/gradient 等价；这些要求并不
  涉及任意全模型 primitive。
- `Add` 和 `RMSNorm` 都无 effect。effectful recompute 拒绝来自区域声明 effects 的
  并集，不依赖内部 primitive 可见性。

## 判断

B 的挑战不能构成保留 fine MathGraph 的证据。最小 contract 可以是：

```text
ResidualNormRegion
inputs:  x, residual, weight
outputs: normalized, summed
effects: none
variants:
  unfused = add + rmsnorm
  fused   = residual_rmsnorm custom op
backward:
  variant-owned saved state/VJP
provenance:
  semantic region + selected variant
```

两种 variant 产生同一个 normalized Program 节点；区别记录在 implementation identity，
而不是 Program 拓扑。这里没有可供调度器插入工作的 collective 或 effect，因此隐藏
region 内部的 `Add → RMSNorm` 不损失现有调度自由度。

现有测试也可平移：

- 双向 rewrite 测试改成同一 semantic region 的 variant 选择测试；
- provenance 记录 `ResidualNormRegion(unfused|fused)` 及模型 scope；
- loss/gradient 继续对 plain-torch reference；
- recompute verifier 读取 region contract 的 effects 和 saved-state policy。

真正风险不是表达不了该 fusion，而是每遇到一个局部模式就新增一个 region，最终把
RegionGraph 重新膨胀成 primitive IR。

## 待验证假设

- semantic region 数量可以按“调度边界、effect 边界或独立 implementation 选择”限制，
  而不是按每个 tensor operation 增长。
- variant 内部可由普通 PyTorch、custom op 或 region-local compilation 实现，不向
  全局 planner 暴露 fine graph。
- 若未来需要在 residual add 与 norm 之间插入调度、独立 recompute 或跨算子 fusion，
  这一 region 才需要重新拆分；当前代码和近期 milestone 没有该需求。

## 决定

`continue`。B 已让步于近期不存在必须依赖 primitive MathGraph 的 transform；下一轮
的新问题应从“能否表达”转向“如何机械限制 RegionGraph 不退化”。
