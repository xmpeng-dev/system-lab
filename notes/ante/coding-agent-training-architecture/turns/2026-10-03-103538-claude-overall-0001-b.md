## 发言

### 事实（已在代码中核对）

1. **gfx950-only 有 startup 断言。** `cairn/arch.py:17` 定义 `SUPPORTED = "gfx950"`；`detect()`（约
   60–70 行）在 `gcnArchName != SUPPORTED` 时 `raise RuntimeError`，报错文本写明「扩展这个模块和
   precision recipes，不要在别处加 fallback」。树内唯一的 `gfx942` 在 `cairn/kernels/attention.py:165`，
   是一个字符串；我没有展开上下文，**待 C 核实它不是 fallback 分支**。
2. **无跨节点 EP 有 startup 检查。** `cairn/record.py:58` 的 `resolve_topology` 在
   `ep_size > local_world_size or local_world_size % ep_size` 时报错（"cross-node expert parallelism is
   outside Cairn's design"）。`write_run_record`（约 509 行）在 `LOCAL_WORLD_SIZE` 未设置时拒绝运行，
   因为仅凭 world size 证明不了 EP 留在节点内。`tests/contracts/test_record.py` 覆盖了
   `resolve_topology`。
3. **CP 只是预留。** `record.py:371` 对 `context_parallel_size != 1` 报错（尚未接线）。mesh 固定为
   `("pp","dp","cp","ep")`（`modules/distributed.py:154-157`），没有 TP 维；在 `cairn/` 下 grep
   `tensor_parallel|tp_size` 无结果。
4. **search 的对象存在，search 本身不存在。** `cairn/compiler/implementation.py:33` 的 frozen
   `Implementation` 有六个字段（scheduler / moe / fusions / recompute / residency / kernels），
   `describe()` 写入 `run.json`；树内没有 search 循环（grep `def search` 无结果）。
5. **度量有守门。** `bench/regression.toml` 登记两个 regime（Qwen3 floor 3400，DSv3 floor 23000），
   每条都带 torch 版本与 `hw_queues`；`[[unreproduced]]` 把 6045 明确标为「不要当作已保持」。

### 判断

- **这些边界互相支撑，不是各自独立的选择。**
  - EP 在节点内 → all-to-all 只走 xGMI → `single_overlap` 和 lane merging 可以在一个已知带宽域里
    做调度决策，不必建模 NIC。
  - 单一 arch → `tuning/gfx950.json` 可以缺 key 就 raise，不需要为两个目标维护两套 tile。
  - 拿掉任何一条，其他条的简化就站不住。
- **推迟 Optimize 是正确的顺序。** 先让 `Implementation` 成为一个 run 唯一的决定对象并被记录，
  search 才有可变异的对象和可比较的证据（`run.json` + `events.jsonl` + `check_regression.py`）。
  AGENTS.md 的 MoE 行就是一次手动的「search 一步」：只改 `Implementation.moe` 一个字段，比较
  dynamic / static / fused。这个对象已经被当作 search 单位用过。
- **在这个硬件上，无 TP 有依据。** 单节点 8×MI355X 显存够大（DSv3 4-layer 峰值 191 GiB），FSDP 加
  EP 就能装下目前跑的两个模型。

### 待验证假设 / 证据的终点

- **Train-only 与无 TP 没有代码层面的强制。** 它们只是 AGENTS.md「Do not land」清单里的产品约定，
  靠 review（skill `review-cairn-change`）守，不是 startup 检查。我承认这两条是约定，不是机制。
- **「无 TP 足够」只在 4-layer DSv3 和 Qwen3-30B 上成立。** 完整 61 层 DSv3 在单节点、EP 不跨节点的
  前提下能否装下，我没有任何测量。这个前提一旦被打破，边界的成本才会显现——跨节点 EP 被禁止，
  意味着扩规模只能靠 DP/PP。
- **吞吐证据的可信度有限。** status 表里的 5817 / 31111 等数字，我没有看到对应的 `logging/` 产物，
  只看到 regression.toml 的 floor。另外 `cairn/ir`、`cairn/runtime` 和 `cairn/compiler` 的大部分文件在
  git 中未跟踪（`??`），所以「built」指的是工作树，不是任何已提交版本。
