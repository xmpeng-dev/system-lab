# B：「digest 确定执行」不成立，我让步；守得住的是更窄的一句——runtime 不做选择，但执行由三层共同决定

我是 B（Architecture Advocate），由 Claude orchestrator 启动的 general-purpose subagent。本 turn 只读代码，
另在 `xiaoming-dev` 容器里跑了一个 CPU 探针（`/tmp/bprobe/dig.py`）。

## 我回应的命题

C（turn 4）的命题：`CompiledProgram` + `run.json` 是一次运行完整且唯一的描述；给定 digest，执行就
确定了。C 的反例：digest 不含 effects、waits、frees、units 和 loss 公式。

## 发言

### 事实

1. **C 的反例成立，实际范围更大。**
   - `_program_digest`（`compiler/compile.py:135-143`）每个 task 只哈希
     `label|chunk|mb|reads|writes`，而 `ComputeTask.label` 只是 phase 加 op 类型名
     （`ir/exec.py:107-109`）。
   - 探针（Qwen3、`Single`、`ep=8`、`num_mb=2`）逐项清空或翻转 `frees`、`waits`、`drop_saved`、
     `units`，四次 digest 都**不变**。
   - 只把 `KernelBinding.attention` 换成另一个 impl，digest 也**不变**，只有 `bindings` 字段不同。
   - 相反，`autograd_vjp=(Linear,)` 会改变 digest，因为它改变了 autodiff 产出的图。
2. **effects 其实间接在 digest 里。** graph digest 哈希 `op.describe()`（dataclass repr，
   `ir/graph.py:275-309`），而 effects 是 op 字段的纯函数。例外是 `GroupedGemm.module` 为
   `compare=False, repr=False`（`ops.py:652`），所以 `convert_for_recipe` 换精度模块后，graph digest
   预计不变——这一点仅读码，**未用探针验证**。
3. **loss 公式只有一半在 Program 里。** `CrossEntropy`（summed）加 objective seed 进入 graph digest
   （`pretrain.py:80-91`）；「除以全局非 ignore token 数」在 `cairn/gradients.py` 和 `train_step` 里，
   不在 Program，也不在 digest。
4. **`Runtime.__init__` 在 setup 阶段解析的东西**（`runtime/executor.py:76-145`）：
   - `impl = binding.for_op(op)`：由 `Implementation.kernels` 完全决定；
   - `Env(device, ep_group)`：读自 `contexts.distributed`；
   - `_peer`：`dist.get_global_rank(pp_group, r)`，可由 `run.json` 的 mesh 推出；
   - `FSDPResidency(modules, program.units)`；
   - `flops_per_token`：仅用于计量；
   - `_connect_peers`：按 channel 的 peer 做一轮对称握手 send/recv。这是 runtime 自己加的通信，
     **不在 Program 里**，`verify_programs` 也不检查，但可由 `channels` 推出；
   - stream 策略：「collective 从 compute stream 发出」写死在 executor 代码里，**既不是 Program 字段，
     也不是 `Implementation` 字段**。

### 判断：三层划分

| 层 | 内容 | 记录位置 |
|---|---|---|
| A. Program 完全决定 | task 顺序、slot 读写/释放、waits、save/drop、units、channels、每个 op 的 impl | `run.json` 的 `program`（含 `order`/`channels`/`units`/`bindings`）记录了大部分；**digest 只覆盖其中一个子集** |
| B. cfg + 环境决定，已记录 | mesh/topology、batch split、recipe、`Implementation.describe()`、torch/hip 版本、`GPU_MAX_HW_QUEUES`、hipBLASLt workspace、tuning 文件的 arch 与行数 | `run.json`（`record.py:180-220`） |
| C. 运行时决定，未记录 | 数据决定的 splits（`HostSplits` 的 `.tolist()`）；RCCL 算法/协议；hipBLASLt heuristic 选中的 kernel；aiter 内部 kernel dispatch；Triton autotune 结果（`kernels/attention.py:515`）。另外 `run.json` 不记录 triton/aiter/flydsl 版本、`NCCL_*`/`RCCL_*` 环境变量、`tuning/gfx950.json` 内容哈希和 git sha（grep 均无结果）——而当前 `cairn/runtime` 本身还是 untracked | — |

我收窄命题：**runtime 不做选择**——executor 里没有一处分支看 scheduler、overlap 或 kernel，这点我
坚持。但「digest = 执行身份」是错的，「Program + `run.json` 是完整描述」也是错的。C 层是 runtime
之下的库和硬件的选择，Cairn 的架构本就不打算把它们拉进 Program；其中 splits 本质上是数据，也不该
进 Program。

### 待验证假设

- 三处廉价修补可以让 A、B 两层真正封闭，不需要改架构（**均未做原型**）：
  1. digest 改为哈希每个 task 的完整 dataclass 字段，再加 `Implementation.describe()`、loss 归一化
     方式和 stream 策略常量；
  2. `run.json` 增加 triton/aiter/flydsl 版本、RCCL 环境变量、tuning 文件哈希和 git sha；
  3. 修复上个 run 发现的问题：`bindings` 现在是「每个类型取最后一个」，应改为按 node 记录。
- C 层中 RCCL、hipBLASLt 的选择会不会让同一个 `run.json` 两次运行的吞吐相差超过 3%，我**没有**
  证据。已知 run-to-run 约 1%、跨节点约 3%（`bench/regression.toml` 注释），都未归因到 C 层。
