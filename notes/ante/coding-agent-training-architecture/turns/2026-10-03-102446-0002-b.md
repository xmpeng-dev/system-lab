## 发言

### 事实（已在 CPU 上核实）

1. `merge` 的输入只有两条 lane 序列：`merge(F, B)` 与 `merged_pair` 取出的序列逐元素相同
   （Qwen3、DSV3 均为 True）。
2. 四个调度谓词读取的信息：
   - `hands_over`：只看 `CollectiveTask` 的输出是否为 float；
   - `waits_on_metadata`：`ComputeTask` 是否读了非 activation collective 的输出；
   - `host_reads_a_collective`：`HostSync` effect 加 collective 输入；
   - `defer_metadata_waits`：另外检查被越过的 task 是否读取被移动 task 的输出。

   它们都不看非边界 compute 的 op 类型。**例外是 `_ahead`**：它数对方 lane 到下一个 collective 前
   非 collective task 的**个数**，再取 0.25（exec.py:410-428，docstring 原文 "A share of tasks,
   since the compiler has no cost model"）。
3. 粒度：Qwen3 一个 F lane 278 个 task，其中 attention 113 个、7 种类型、无 collective；DSV3 F lane
   347 个，attention 161 个、9 种类型。MoE 的 F 侧（dispatch/experts/combine/aggregate）发出 11 种
   op 类型，只有 4 种被调度谓词区别对待：`CountsExchange`、`AllToAll`、`HostSplits`、`LocalExperts`。
   `DispatchPlan`、`DispatchGather`、`ExpertSort`、`GroupedGemm`、`ExpertSiluMul`、`ExpertUnsort`、
   `MoeAggregate` 在调度里只作为计数出现。
4. 反例实验：把每条 lane 在 collective / host-read / metadata-wait 之间的 compute 段压成一个 task
   （Qwen3 278/335 → 73/33），再跑 `merge`：
   - 每个 host read 前对方 lane 先跑的 task 数，从 `[2,7,7,…]`（Qwen3）、`[2,11,11,…]`（DSV3）
     全部变为 **0**；
   - 这正是 `test_the_other_lane_runs_ahead_of_a_host_read` 断言不能发生的情况；
   - next-work row 1 归因于此的 29381 → 29626/29711（DSV3，单节点）会丢失。
5. 0.25 是在**当前 task 个数**上扫出来的：1/8 → 29286，1/4 → 29626/29711，1/2 → 29370。它与
   per-op 粒度隐式耦合：任何 fusion 都会悄悄改变它的含义，例如 `FuseResidualNorm` 每层减少
   task，`_ahead` 随之改变。
6. 成本侧：`cairn/ir/ops.py` 40 个 class，`cairn/runtime/impls.py` 40 个 class，ir+compiler+runtime
   共 6293 行。`git status` 确认 `cairn/ir/`、`cairn/runtime/`，以及 compiler 中除 `partition.py`
   （已 staged）外的文件都是 `??`（untracked）。A 的事实 6 成立。

### 判断

- **A 的第一问按字面回答是「不能」**。「完全相同的 Program」以 task 序列为单位：段内一旦是
  opaque task，Program 就不同，`_ahead` 也会退化为 0。
- **但这推不出「需要 primitive IR」**。缺的只是对方段的一个切点或权重：region 声明 `ahead_split`
  或 per-segment cost，就能表达同样的调度意图，而且比数 task 更诚实，因为 task 个数本来就是
  cost 的代理。A 把「需要细粒度 task」和「需要细粒度 op 类型」混在了一起。
- **A 的第二问：今天逐 op 生成 MoE 序列的确实是 primitive IR**（`moe.py` 的 `Rewriter.emit`）。但
  需要这个粒度的不是调度，而是 **autodiff（逐 op 显式 VJP）和 kernel binding**。MoE 的 11 种
  类型中 7 种对调度不可见，所以 primitive IR 的存在理由要到 autodiff/binding 那边论证，不能拿
  `merge` 当论据。
- `FusedMoE` 的 −9.5% 也不支持「必须 primitive」。它的代价是 all-to-all 被包进 compute task、
  失去 lane 切换点（next-work:57-58），丢的是**边界**，不是 op 类型。

### 待验证假设

- H3：把 `_ahead` 改为「按 region 声明的 cost 权重」后，在当前 per-op Program 上算出的 ahead 应能
  复现 `[2,7,7,…]`。如果做不到，说明 0.25 编码的是 task 粒度的偶然性。
- H4：若 region =「边界之间一个 task + dgrad/wgrad 入口」，要让 `defer_metadata_waits` 等价，
  `LocalExperts` 与 `HostSplits` 必须各自是独立 task，即 region lowering 至少要在 metadata consumer
  处切开。这需要逐条核对 `defer` 的数据依赖检查。

### 给 C：应保留

- typed Program task 层，以及 `TensorSpec.is_float`、`HostSync`、collective 声明（调度和 verifier
  都依赖它们）；
- `merge` / `defer_metadata_waits` 作为 lane 序列上的纯函数；
- 边界处的细粒度：collective、host read、metadata consumer。

### 给 C：应拒绝

- 「`hands_over` / `defer` 证明需要 primitive MathGraph」——它们不看非边界 op；
- 不附 cost 声明的「region = 边界之间一个 opaque task」——会直接打掉 `AHEAD_OF_A_READ`；
- 把 `_ahead` 的 task 计数当成稳定语义——那是未声明的粒度耦合。
