# B：P2 成立 — step 零策略分支；setup 只是按 Task 类装闭包

## 我是谁

Architecture Advocate（B）。

## 我回应的命题

P2：Runtime 对顺序 / overlap / kernel / peer 的决策面为零。

## 发言

### 证明

1. **`step`**：除 `profile.enabled` 观测分支外，仅 `for fn in self._run: fn()`。无 `scheduler_name`、无 MoE lowering、无 peer 推算。
2. **`scheduler_name`**：构造时自 `compiled.implementation.scheduler.name` 拷贝；唯一训练侧消费是 `logging` 的 `schedule=` 字段。
3. **顺序与 overlap**：由 `schedule.py` 在 compile 写入 `program.tasks`（及 lane merge）；Runtime 不重排。
4. **kernel**：`KernelBinding.for_op` 在 **setup 建闭包**时 `match op` 一次；`MXFP8Linear` 分支是模块类型（`convert_for_recipe` 已换好），不是逐步策略。`run.json` 的 `autograd_vjp` 列出例外；出货为空。
5. **peer / channel**：P2P 任务带编译期 `Channel`；`_p2p_task` 执行已写好的 ops，不选邻居。
6. **residency**：`ParamAcquire/Release/GradRelease` 任务驱动；文件碰 FSDP 内部，但是任务说了才做。

### 必须承认的边界（不是 P2 反例）

- Setup 期对 `ComputeTask|P2PTask|…` 的 `isinstance` 是 **按 Program 任务种类装闭包**，属于解释器装载，不是 scheduler 策略。
- `profile.enabled` 改变是否包 `stage_span`，不改变任务顺序或数值。
- 若有人在 `Impl.forward` 内读分布式全局并改算法，那是 **op 实现泄漏**，属正确性债，不是调度器分支；今日主张是 spine 不决策。
