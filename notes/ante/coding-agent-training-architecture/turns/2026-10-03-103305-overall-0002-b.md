## 发言

### 论证：同意，且必须改“读起来像现货”的愿景句

**事实**

1. 可执行路径止于 `compile_rank` → `Program` → `Runtime.step`。`Implementation` 是六类 compile policy（`moe/fusions/recompute/residency/scheduler/kernels`），由 `resolve_implementation` 从 cfg 一次建成，**没有**候选生成、测量闭环或 evidence store 读写。
2. `AGENTS.md` / `next-work.md` 将 search、Primus adapter、tune/bench 命令标为 **not built / Not now**；硬约束禁止 search 进入 train loop。
3. `docs/architecture.md` 仍用现在时画 L2 Search 与 transform 目录，读起来像系统能力，与 checkout 不符。

**判断**

产品边界若对 coding-agent 诚实，应分层：

| 层 | 状态 | agent 应读到的措辞 |
|---|---|---|
| Train spine | **built** | “runs / holds / measured” |
| Run record + floors | **built** | 归因与守卫 |
| Optimize / Search / evidence | **not built** | “product target / do not implement inside train” |
| Primus adapter | **forbidden until pinned run** | FAIL list |

这样与代码自洽：`Implementation` 仍是**搜索若存在时会 mutate 的对象形状**，但今日它只是 cfg→compiler 的决议记录。保留该对象不等于交付 Search。

**最小 Optimize 切片？** 本轮论证：**不要**。在 RegionGraph / floor / kernel 债未清前开 Search，会把未验证的变换空间写进 agent 上下文，违反“config 错误启动失败、runtime 不决策”。若 Owner 将来要切片，最小也只能是 **离线、只读 `run.json`+`kernels.json` 的归因报告**，仍不是 accept 闭环。
