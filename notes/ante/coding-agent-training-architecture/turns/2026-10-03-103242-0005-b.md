## 发言

### 事实（已核实）

1. **binding 与 A 所述一致。** `binding.py:132-135` 按 `op.module` 是否为 `MXFP8GroupedLinear`
   选择 Impl；`:146-147` 无条件返回 `FUSED_ROUTED_EXPERTS`。
2. **`FusedRoutedExpertsImpl` 绕开了 binding。** 它（`impls.py:628-`）直接调用 bf16 的
   `grouped_gemm`。它的 docstring 说 "Built from the same implementations the finer lowering
   binds"：对 kernel 函数而言成立，但 Impl 与 binding 不同，所以在精度这一维上不成立。
3. **H5 在 CPU 上成立。** 对 Qwen3 和 DSV3 都编译了 `convert_for_recipe(MX_FP8)` + `FusedMoE` +
   `SingleOverlap`（ep=8）：
   - 编译与 verify 全部通过，没有任何拒绝；
   - bindings 记为 `FusedRoutedExperts -> FusedRoutedExpertsImpl`；
   - 该 op 的 `experts.gate_proj` 确实是 `MXFP8GroupedLinear`；
   - 仓库中只有 `training.py:105` 一处提到 `FusedMoE`，不含拒绝。

   限定：今天这个组合**不会产出标错精度的完整 run**——attention 的 `Linear` 已被换成
   `MXFP8Linear`，执行到它的 kernel 时会先 raise。所以 H5 是**潜伏**缺陷：一旦 `MXFP8Linear` 的
   kernel 先于 grouped MX kernel 落地，它就会变成真实的错误标签。
4. **H6 成立，只需改 1 个文件。** `FusedRoutedExperts` 带 `experts` 字段（`ops.py:811`，由 `moe.py`
   的 FusedMoE lowering 传入）。在 `impls.py` 加一个按 `isinstance(module, MXFP8GroupedLinear)`
   分派的 helper，替换 fwd 3 处、dgrad 3 处、wgrad 3 处调用，即可在到达 MX kernel 时 raise；
   不需要新增 IR，也不需要新增 binding 的 case。
5. **这个 helper 其实已经写过一份。** `ops/grouped_linear.py:43-127` 的 `GroupedLinearFunc` /
   `MXFP8GroupedLinearFunc` 正是「按 module 类型分派、逐方向写好」的 expert GEMM，但训练路径
   不调用它们，只有 `tests/contracts/test_recipes.py` 引用。结果 expert GEMM 的求导现在有
   **三份**：
   - `GroupedGemmImpl` + `MXFP8GroupedGemmImpl`；
   - `*GroupedLinearFunc`；
   - `FusedRoutedExpertsImpl`。

   H5 的根源是这种重复，不是 region 设计。
6. **新发现：per-op 的运行记录也说不清实际 binding。** `compile.py:211-218` 的 bindings 以 op
   **类型名**为 key，后写入的覆盖先写入的。Qwen3 + MX_FP8 下，前向 `Linear` task 中 64 个绑定到
   `MXFP8LinearImpl`、2 个（`lm_head`）绑定到 `TorchLinear`，`run.json` 却只记成
   `Linear -> TorchLinear`。所以「per-op binding 让记录说出实际运行了什么」今天本身不成立。

### 判断：38 个 op 的分类

我不同意把 20 个 op 一律算作「仍需手写 VJP」，应拆成三档：

- **只是链式粘合，不算 VJP**：例如 `Add` 的 dgrad 是 `(g, g)`（`impls.py:311-312`），`AddN` 同理。
- **backward 是 owned kernel，但 W 与 dgrad 已融合**：例如 `ResidualRMSNorm` 是
  `fused_backward = True`，dw 在 dgrad 内部累加（`:283-303`），调度上本来就无法推迟 W。这类在
  region 里用 `autograd.Function` 包装 owned kernel、由 autograd 链式组合，在语义上已足够。
- **必须暴露独立 W 入口**：按 C 在 turn 3 的统计，`dualpipe_v` 推迟的 W 只有 `GroupedGemm`、
  `Linear`、`Embedding`，共 3 个。

AGENTS.md:244 把 `AutogradVjp` 定为 bring-up only。它针对的是「对可微 torch forward 做
autograd」，代价是保存局部图（`impls.py:761-767`）；对 owned `Function` 做 autograd 时，保存什么
由 `ctx` 决定，所以这条规则字面上不覆盖第二档。

但我让步一点：region 内部一旦交给 autograd，saved tensor 就脱离 `memory` pass 与 verifier 的
residency 检查，「由静态 Program 记账」的性质会丢掉一部分。这是真实成本，要靠测量定价，不能
靠论证。

### 结论

- **正交性论据失效**：分派只要写在一处（helper 或 binding 的 `case`），两种设计的改动点都是
  3+2。H5 是重复实现造成的，不是 region 粒度造成的。
- **region 设计还缺一条声明**：region impl 必须向 `run.json` 报告每个调用点用了哪个 kernel，
  否则精度在 region 内部不可见。per-op 设计今天也缺同一条（事实 6）。
- **per-op IR 剩下的可辩护范围很窄**：
  - 5 个切点类 op；
  - 3 个可推迟 W 的 op；
  - 以上两项在 Program 层就能表达，不需要 primitive IR；
  - 静态 saved-tensor 记账，需测量定价。

### 给 C：应保留

- typed Program、切点 task 和独立 W task；
- verifier 与 `memory` pass 对 saved tensor 的静态记账——在没有测量之前，不允许 region 内部默认
  交给 autograd；
- 每种 GEMM 的精度分派**只写一处**。

### 给 C：应拒绝

- 「per-op binding 因正交性而必要」——事实 4、5 已反驳；
- 「20 个 op 都需手写 VJP」——真正必须拆出独立 W 入口的只有 3 个；
- 「`run.json` 的 bindings 记录了实际精度」——事实 6 已反驳。
