# C：`train_step` 本身没有任何测试执行——删掉一行 reset 就能改变梯度，并且全部测试仍然通过

## 我是谁

Claude（Opus 5.5），本 run 的 C。

## 我回应的命题

B（turn 9）：真正的缺口在「声明和记录是否与实现一致」；补三类 CPU contract 比加 GPU 端到端测试更有
价值。B 请我找一个会改变梯度、却能通过 4 层单步引擎测试的错误。

## 发言

### 反例：组合根 `train_step` 不在任何测试路径上

- `tests/` 下没有任何文件调用 `train_step`（`grep -rn train_step tests` 只命中两处注释）。
- 引擎测试和 pipeline 测试调用的是 `runtime.step`（B 事实 1），不经过 `train_step`。
- `test_learning.py` 在 `:148-170` **手工复刻**了 `train_step` 的逻辑——注释原文是 "exactly as
  `train_step` does it"——并且在 `:167` 自己调用 `LoadBalanceTracker.reset()`。

因此，删除 `cairn/pretrain.py:187` 的 `LoadBalanceTracker.reset()` 后：

- 全部现有测试仍然通过：引擎测试是单步，`test_learning` 用的是自己的副本；
- 真实训练中，global-batch 公式的 expert 计数会**跨步累积**，从第 2 步起 router 的梯度就错了；
- loss 曲线可能只是略差——而 B 事实 4 已经说明，没有工具守护 loss。

这正是 B 要的「改变梯度、却通过 4 层单步测试」的错误。这一类不止一个：`train_step` 里的梯度
归一化（除以全局 token 数）、clip、optimizer step、lr scheduler、`GC_INTERVAL`/`gc.freeze`，**每一行都是
组合根代码，而测试只验证它们的副本**。agent 改 `train_step`，是 AGENTS.md 允许、也最常见的一类
改动。

### 对 B 三类 CPU contract 的修正

- **「声明 vs 实现」不能在 CPU 上做**：我在 turn 4 已说明，host sync 和 collective 藏在 helper 里
  （`ops/ep_dispatch.py:100`、`direct_all_to_all`），grep 只能做启发式。可靠的做法是在 GPU 引擎测试中
  按 task 记录实际发生的 collective / host sync，再与声明对照。所以 B 的三类里有一类**必须**进 GPU 测试。
- **「记录 vs 实际」「digest 敏感性」可以在 CPU 上做**，同意，代价也低。

### 议题结论：正确性 — **resolved（定位清楚，缺口可列举）**

- **强项**（B 坚持的部分，我同意）：「数学改错」类——VJP、seam、梯度路径、residency 窗口——由独立
  reference 的逐梯度对比与 96 个调度 verify case 守护。
- **结构性缺口**（按优先级）：
  1. **组合根无测试**：引擎测试应改为调用真实的 `train_step`（N≥3 步，含 reset、归一化、optimizer），
     而不是测试副本。可以用 `test_learning` 的 Markov 设置，并把手工复刻的部分删掉。
  2. **loss 无守护**：`check_regression.py` 增加 loss 轨迹检查（例如第 120 步的 loss 在登记值的容差内），
     数据就在 `events.jsonl`。
  3. **声明与记录**：bindings 按 node 记录、digest 变异敏感性测试放在 CPU；effect 声明与实际的对照放在
     GPU 引擎测试。
  4. **Muon 多步 reference**：待验证可行性。
- **观察**：8 个缺陷 0 个由事先存在的测试发现。这本身不是坏事——review 和讨论在发现，测试在锁定
  ——但它意味着 agent 改动后「测试全绿」**不等于**没有引入这几类错误，AGENTS.md 应写明这一点。
