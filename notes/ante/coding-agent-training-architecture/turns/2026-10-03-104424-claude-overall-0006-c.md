### 反例：Cairn 自己的代码在每次调用时做选择

`cairn/kernels/grouped_gemm.py` 的 `grouped_gemm()` 每次调用都执行：

```python
cfg = params or launch_config(trans_b, M_total, N, K, a.dtype)
```

- `launch_config` 调用 `tuning.variant(op, m, n, k)` 和 `tuning.params(...)`（`grouped_gemm.py:45-63`）；
- 查表键里的 `M` 是 `bucket_m(M_total)`（`tuning.py:48-58`），即把行数向上取到 2 的幂；
- 在 dynamic lowering 下，`M_total` 是本 micro-batch 路由收到的行数，由数据决定、每步变化；
  `bucket_m` 的 docstring 自己也写了 "Per-expert token counts move every micro-batch — routing is
  data"；
- `grouped_gemm_wgrad.py:62-69` 是同样的模式。

所以**选哪个 tile（以及哪个 variant）是 Cairn 自己的代码在运行时、按数据做出的选择**。它不在
`Implementation` 里，不在 Program 里，也不按步记录——`run.json` 只记录 `tuning_rows` 的数量和
`tuning_measured`。AGENTS.md:349 说 "`tuning/gfx950.json` is looked up once at startup"，与代码不符：
文件只在启动时**加载**一次，**查询**发生在每次 kernel 调用时。

**今天它为什么没有生效**：我把 `tuning/gfx950.json` 中所有 grouped GEMM 条目列了出来——
`grouped_gemm_fwd` 有 3 条、`grouped_gemm_dgrad` 1 条、`grouped_gemm_wgrad` 1 条，`m_bucket` 全部是
`null`（`generated_by`：「seeded by hand…no sweep has run on this machine」）。也就是说任何 M 都命中
同一行，选择是常量。一旦按 status 表与 next-work 的方向跑一次 sweep、写入按 M 分桶的行，每一步的
tile 就会随路由跳动，而记录里看不出来。

**所以 B 的论断只对了一半。** 库内部的选择（RCCL、hipBLASLt、aiter）属于环境，记录版本即可，我同意。
但 tuning 查表是 Cairn 自有代码，而且这个机制**设计上**就是运行时决策——只是表还没填。「runtime
decides nothing」在 executor 层成立，在 kernel 的 launch 层不成立。

这件事有两种合法修法，需要 Owner 选择：

1. **承认它是有界的数据依赖选择**：像 splits 一样把它当成数据，但要可观测——`profile.json` / `events.jsonl`
   按步记录每个 GEMM 命中的 tuning 行。规则（表本身）进入 `run.json`（内容哈希）。
2. **提升为编译期决定**：在 `Implementation.kernels` 里固定 tile（每个 shape 只用一行），放弃按 M 分桶。
   代价是动态路由下行数变化很大时，无法按 M 调优。

我倾向 1：splits 已经是同类先例，而「表的内容哈希 + 按步命中记录」恰好闭合 B 在第 C 层提出的记录缺口。

### 议题结论：compiler/runtime — **resolved（executor 不做选择；三处记录缺口；一处运行时选择需 Owner 定性）**

- **成立**：executor 不按 scheduler、overlap 或 kernel 分支；binding 在 setup 时由 `Implementation`
  确定；peer 由 mesh 推出。
- **不成立**：「digest = 执行身份」「Program + `run.json` = 完整描述」。
- **修补（局部）**：
  1. digest 覆盖 task 全字段与 `Implementation.describe()`；
  2. `run.json` 增加库版本、RCCL 环境变量、tuning 内容哈希和源码版本（与议题 1 合并）；
  3. bindings 按节点记录。
- **需要 Owner 定性**：tuning 查表属于「有界的数据依赖选择」还是「编译期决定」；同时修正 AGENTS.md:349
  的描述。
- 附带：`_connect_peers` 的握手通信不在 Program 里。它是 RCCL 建连的变通，可以由 channels 推出，属于
  可接受的执行细节，不算决策。
