## 发言

### 事实

1. **数字能复算。** 容器内对已有目录运行检查器，结果与 AGENTS.md status 行一致：

   | 运行目录 | median | 是否超过 floor | total |
   |---|---|---|---|
   | `logging/row1/n29_gg_qwen3/qwen3-30b-a3b` | 5817 tok/s/GPU，134.3 TFLOP/s | PASS，高出 71.1% | 4855 |
   | `logging/row1/n29_gg_dsv3/deepseek-v3-4layer` | 31111，639.8 TFLOP/s | PASS，高出 35.3% | 30167 |

   另外 `n29_flydsl_qwen3` 的 median 为 5595。检查器按 config、mesh、tokens/step、recipe 判断两个
   run 是否属于同一 regime（`check_regression.py:93-104`）；torch 版本或 `hw_queues` 不一致时拒绝
   比较，返回 exit 2（`:155-171`）。
2. **`run.json` 有 33 个顶层字段**，覆盖 `implementation`（scheduler/moe/residency/kernels）、topology、

   triton/aiter/flydsl 版本、tuning 内容哈希（turn 5 已指出）。regime 匹配也不看 `implementation`，所以
   同一个 config 下换一种 lowering 跑出的数字，会和同一个 floor 比较。
3. **floor 的来历**：
   - Qwen3 的 3400 来自 2026-09-01 的两次运行（median 3508、3473），原文写 "Floor is under both
     medians and under the slowest step"，之后再未上调。

4. **`bench/kernels.json`**：85 行，每行以 (op, impl, shape) 为键，带 torch/hip/flydsl 版本、gfx、host
   和测量日期，分散在 7 个日期、至少 2 台 host。grouped GEMM 的 offsets 是均匀的
   `arange(G+1)*(M//G)`（`bench/ops.py:34`），shape 取自 `tests/kernels`（`:63`、`:84-87`）。
5. **检查器在 Python 3.10 下崩溃**：host 是 Python 3.10，`import tomllib` 失败，以 **exit 1** 退出——
   而按它自己的约定，exit 1 的意思是「floor broke」。这是一个小缺陷，但恰好是它 docstring 所说的
   "guard starts lying"。

### 判断

- **反证 1：让步。** 证据链能把一个数字归因到「请求了什么、解析成什么、在什么 toolchain 和几条 hw
  queue 上跑」，但不能归因到源码版本和 host（例如 n01-29 与 n01-21 约 3% 的差距只写在 prose 里，
  没进 record）。在 compiler/runtime 未被 git 跟踪的情况下，「可复算」只到算术层面，执行层面不可
  复现。
- **反证 2：让步。** 只记录了 tuning 的行数，没有内容。
- **反证 3：完全让步，而且比 C 说的更严重。** 按 DSv3 行自己写下的规则——「被树超过 11% 的 floor
  守不住任何东西」——Qwen3 被超过 71%、DSv3 被超过 35%，**两条 floor 都已经不守了**。我能为 3400
  找到的唯一辩护是「它是同一 toolchain 下第一次有记录的测量」；但旁边已经有 n29_gg 的完整 artifact
  可以定新 floor，却没有定。还有：检查器只用 median 判 PASS，Qwen3 的 total 比 median 低 17%
  （4855 对 5817），慢的那一档步数完全不进入判断。
- **反证 4：部分让步。** 这张表不是 step 的时间分解，也不能预测真实路由下 kernel 能跑到的速率
  （470 对 583–888），AGENTS.md 自己也这么说。但它支持过一次决策：同一 session、同一 shape 下
  incumbent 与 challenger 的比较（如 qwen3 gate/up fwd，FlyDSL 652 对 torch 234 TFLOP/s），这个相对
  判断后来被端到端结果证实（5129–5146 → 5817）。所以它能回答「换不换 kernel」，不能回答「step 时间
  花在哪」——后者是 `profile.json`/`kernels.json` 的职责。

### 待验证假设

- 以下 record 与 toml 层面的改动应能补上反证 1–3 的大部分，不涉及架构（未做原型）：
  - `run.json` 加 git sha、dirty 标记、hostname、各库版本、tuning 文件哈希；
  - regime 匹配加入 `implementation`；
  - floor 改为按 n29_gg artifact 的「慢档」来定（类似 DSv3 的做法），而不是只看 median。
- 均匀 offsets 与真实路由的差距，可以通过存下一次运行实际观测的 offs 分布、喂给 `bench/ops.py` 来
  缩小；`profile.json` 的 ops 表已有真实路由下的速率可作对照。可行性未验证。
