# B：当前没有必须依赖 primitive MathGraph 的 transform

## 我是谁

我是 Compiler Advocate，一名审查 Cairn 的 general-purpose coding subagent。本轮只
回应 A 的具体挑战。

## 我回应的命题

> 指出一个当前已实现或未来两个 milestone 已排期、且无法由 region boundary、
> custom-op metadata 或 region-local graph 表达的 transform。

我明确让步：**目前不存在符合该条件的 transform。**

## 事实

- 当前最接近的反例是 `cairn/compiler/fuse.py` 的 `FuseResidualNorm`：匹配
  `Add → RMSNorm`，改写为 `ResidualRMSNorm`；逆变换也已实现。
- 该变换需要观察相邻 primitive，但不需要观察任意全模型 primitive graph。它可以
  表达为相邻 region fusion、一个 fused region implementation，或 region-local
  rewrite。
- 未来两个 milestone 是测量 `interleaved`/`dualpipe_v`，以及替换
  dispatch/combine overlap。两者都作用于 lane、collective、P2P 和 task boundary。
- `next-work.md` 中的 explicit VJP 与 owned kernel 工作可落在 region/custom-op 的
  backward contract 后面；它们尚不能证明全模型 primitive visibility 必要。
- search、transform catalog 和 evidence store 仍是 `Not now`。

## 判断

primitive MathGraph 当前确实统一提供了 shape inference、effects、explicit VJP、
fusion provenance 和逐 pass verification；这是已实现价值。

但这些能力证明了“当前实现完整”，没有证明“RegionGraph 无法以更低维护成本保持同等
契约”。在 A 限定的时间范围内，继续扩张 primitive surface 属于预付复杂度，而非被
近期产品需求驱动的必要成本。

## 待验证假设

RegionGraph 可以保持现有 `Program` 和 verifier，同时把 primitive shape/VJP 责任封装
到 region implementation。其主要失败风险是 region contract 为支持 fusion、
recompute 和 deferred wgrad 不断膨胀，最终在 region 内重建另一套 fine graph。

## 交给下一位

C，请证伪以下挑战：

> 构造最小 RegionGraph contract，在不暴露 `Add`、`RMSNorm` 等 primitive node、也不
> 通过 callback 返回 fine graph 的前提下，完成 `FuseResidualNorm` 的双向选择，并对
> 现有测试矩阵产生等价的 normalized Program、loss/gradient，以及
> effectful-recompute 拒绝结果；任一项无法做到，即构成保留 primitive MathGraph 的
> 近期具体证据。
