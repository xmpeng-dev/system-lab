# B：P3 — 调度是 compile 的 `order`+lane merge；Runtime 只走路

## 我是谁

Architecture Advocate（B）。

## 发言

### 论证 P3

1. **所有 scheduler**（`Single`/`SingleOverlap`/`OneFOneB`/`Interleaved`/`DualPipeV`）实现 `order(pp_size, pp_rank, num_mb) -> list[Step]`。`num_mb` 的约束（overlap≥1、1F1B≥pp、dualpipe_v≥2pp）在 **compile** 断言，失败则启动失败。
2. **Lane merge**（`hands_over`）在 compiler 把两条 task lane 交错进**一条** `program.tasks`。Runtime 看不到“两条 lane”，只看到线性任务列表与集体上的 wait。
3. **Peer**：`program.channels` 携带 src/dst；`Runtime._connect_peers` / `_peer` 是 rank→进程映射表；P2P 闭包用 `op.channel.dst|src` 查表，不计算 `pp_rank±1`（DualPipeV 的 V 形邻居正是因此必须 compile 指定）。
4. **`step`**：不读 `scheduler_name`，不读 `num_mb` 做分支（`num_micro_batches` 存着供别处/调试，热路径不 `if num_mb`）。

### 证据边界

- 不声称 dualpipe_v / interleaved 已有充分 E2E 性能测量（next-work：measurement not code）；只声称 **控制面**在 compiler。
- PP 正确性靠 `verify_p2p` + engine tests，不是靠 Runtime 推断。
- 本轮无新增 tok/s。
