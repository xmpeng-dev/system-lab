## 发言

### 反例：shape 才是缺口，而不是步数

B 要的是「会改变梯度、却通过 `tests/kernels` 与 4 层单步引擎测试」的 row 3 路径。我找到的不是多步
错误，而是**规模**错误：

1. **`tests/kernels/` 里没有任何文件覆盖 `moe_sort` 或 `moe_gather`。**
   `grep -l "moe_sort\|scatter_for_grouped_gemm\|moe_gather" tests/kernels/*.py` 无命中。现有 11 个 kernel
   测试覆盖 attention、grouped GEMM、rmsnorm、aggregate 等，**不包括** row 3 要替换的两个 op。
2. **引擎测试的模型极小**（`tests/test_engine.py:78-120`）：`hidden_size=256`、8 个 expert、top-2、
   `seq_len=128`、batch 4。生产形状是 hidden 2048/7168、128/256 个 expert、top-8、seq 4096。
3. **`port-kernel` skill 不要求生产 shape。** 它要求 torch reference、contract test 和 ledger 行
   （`SKILL.md:42-68`），但没有说测试必须覆盖 regime 的形状。

所以，row 3 的一个 Triton port 若在生产规模上出错，以下情况都会通过 port 自带的测试（形状由作者选）
和引擎测试（宽 256），只在真实 run 中显现：

- 行数超过某个 block 倍数时的尾部处理；
- `PAD_TO` 边界；
- int32 索引在 `rows × hidden` 接近 2³¹ 时溢出；
- 以及最典型的：多个 expert 的 offs 段不对齐。

而真实 run 的 loss，**没有守卫**（turn 10）。这就满足 B 自己设的条件：第 1 层中的 **loss 守卫（第 4
项）**必须前置于 row 3。

**有一个更便宜的替代**：在 `port-kernel` skill 中加入一条要求——kernel 测试必须包含每个已登记 regime
的生产 shape（从 `run.json` 或 `explain` 取），并补上 `moe_sort`/`moe_gather` 现有实现的 reference 测试，
作为 port 之前的基线。这比 loss 守卫更早、更局部地抓住这类错误；loss 守卫仍是兜底。两者择一或都做，
是 Owner 的取舍。
