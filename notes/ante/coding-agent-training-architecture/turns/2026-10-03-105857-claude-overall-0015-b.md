   无法归因。

**第 1 层——阻塞任何改动数学或训练循环的工作：**

4. **loss 守卫**：`check_regression` 对比第 N 步 loss，带容差（turn 10）。

这两项依赖第 3 项：loss 基线需要来自一份可归因的 artifact。

**性能工作现在安全吗？分开回答。**

- **数学正确性：安全。** row 3 的 kernel port 有 `tests/kernels` 的 torch reference 和引擎测试的逐梯度
  对比；它改的是 kernel body，正是这张网最强的地方（turn 9）。
- **作为性能结论：不安全。** 按 next-work 自己的前提，守卫已失效：退步不会被抓到，提升也无法归因到
  源码。

**我的立场**：第 0 层（1→2→3）必须排在 Now 行之前。它们都是 record、toml、git 层面的改动，代价很可能
只有几天（未估算）。完成之前，可以继续写 kernel，但不应再往 status 表写新数字。我承认：next-work 没有
列出这些项，它的 Now 顺序是在本议程这些发现之前定下的。

程序都由人写的 lowering 产出——Sym 判等、effect 漏声明、verifier 的缺口都是如此。一旦 search 开始

**解冻 search 的前提清单：**
