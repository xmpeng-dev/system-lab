## 0. 一句话结论

**这两周没有出现新的 megakernel / 通算重叠工作，热度转移到了两件对我们更实际的事：AMD 自己下场训 MoE，以及 FP4 训练配方开始出现互相矛盾的实证。**

三条主线：

1. **AMD 从零训了一个全开源 MoE 并把整条 model flow 放出来** — [Instella-MoE](https://arxiv.org/abs/2609.00791) `2609.00791`，16B-A2.8B，全程 MI300X + MI325X。这是我们能拿到的、唯一一个"AMD 硬件 + 训练配置 + 数据配比 + 训练代码"齐全的对照点。
2. **AMD kernel 优化出现了绕开源码的新路子** — [AsmEvo](https://arxiv.org/abs/2608.20711) `2608.20711` 直接改已编译的 AMDGPU code object，在 MI300X 上把 **AITer 生产二进制**再榨出 1.09× geomean。这条路线与 FlyDSL「写更好的源码」是正交的，且可以叠加。
3. **FP4 训练配方分歧公开化** — [UE5M3](https://arxiv.org/abs/2609.02846) `2609.02846` 主张**去掉** Hadamard 变换、改用更宽的 E5M3 block scale，而我们 `[papers/mxfp4-pretraining.md](../../papers/mxfp4-pretraining.md)` 在 MI355X 上实测**确定性 Hadamard 才是收敛的必要条件**。这两个结论必须有一个是错的，或者边界不同。**这是本轮最值得投入的交叉校验点。**

同时有三个**负面发现**（见 §7），其中「低精度梯度通信零新增」直接影响我们 9-03 刚建立的 §11 分类的排期。

| **UE5M3 FP4 Block Scaling**             | [2609.02846](https://arxiv.org/abs/2609.02846) | * 09-02 | 反对 NVIDIA Transformer Engine 的 NVFP4 配方（current-tensor scaling + **随机 Hadamard 变换 RHT** + BF16 末层）。改用 E2M1 payload 配 **无符号 E5M3 block scale**：更宽的 scale range 允许**周期性** tensor scaling，**省掉 RHT**、反向只做**选择性**随机舍入、所有合格内部 linear 都跑 FP4 | Nemotron-H 8B 预训练 **约 1900 亿 token**；最终窗口训练 loss 与量化推理 validation loss 均优于 TE 配方；**去掉 RHT + 去掉 BF16 末层豁免后模型主体 token 吞吐 +21.2%**。目前是**软件模拟**，呼吁硬件原生支持 E5M3 block scale |

> **⚠ 必须解决的矛盾**：UE5M3 说**去掉** Hadamard 能得到更稳的 FP4 预训练；我们 `[papers/mxfp4-pretraining.md](../../papers/mxfp4-pretraining.md)` 在 MI355X 原生 MXFP4 上实测**随机舍入与随机 Hadamard 不收敛、确定性 Hadamard 才恢复**。两者并不必然互斥——UE5M3 换掉的是 **scale 格式**（E5M3 vs E8M0/FP8），而 Hadamard 解决的是**离群值分布**；如果更宽的 block scale 本身就吸收了离群值，Hadamard 就变成冗余。**这个假设可以用一个对照实验证伪，且成本很低**，与 §11 里已经排上的「确定性 Hadamard + FP8 wgrad RS」对照组是同一批基础设施。
>
> 另注：`2609.02846` 与 `2609.04105` 第一作者同为 Robert Hu，两篇的 FP4 结论应当合起来看——前者说 FP4 能做全部内部 linear，后者说 FP4 **不能**碰 attention 的 probability/value。
